# CityBrain V2 — Chennai digital twin

V2.2 advisory traffic support is now implemented. See
[CHENNAI_LIVE_TRAFFIC.md](CHENNAI_LIVE_TRAFFIC.md) for offline replay, optional
HERE/TomTom setup, source labels and limitations. Existing SUMO/planner behavior
and the Chennai 20-second guard remain authoritative. Real traffic coverage is
unverified; credentials and explicit request authorization are required.

The Chennai pilot uses actual OpenStreetMap road geometry, SUMO vehicle dynamics,
the existing CityBrain Core/planner/runtime, and a locally bundled CesiumJS view.
It is a simulation and university demonstration, not a live emergency service.
The original 3×3, S08 networks and 180 research trials remain independent.

The V2.1 hotfix adds a Chennai-only soft-proposal confirmation guard. Shared Core,
planner, policy and route execution remain unchanged. The current guard, validated
counts and limitations are documented in [CHENNAI_STABILITY_FIX.md](CHENNAI_STABILITY_FIX.md).

## Architecture

```text
OSM extract → netconvert → Chennai SUMO network
                              ↓ one TraCI connection
                     existing CityBrainRuntime
                    Core → agents → planner → policy
                    execute → read back → accept
                              ↓ read-only observations
        full runtime audit + compact dashboard events + telemetry JSONL
                              ↓ GET-only loopback server
                 existing evidence reducer → CesiumJS
```

Only `citybrain/core/traci_interface.py` extends an existing correctness layer:
it adds a read-only geographical observation method and explicit simulation-only
lane-speed scenario actions. Planner, agents, Core orchestration, route executor,
arrival detection, hysteresis and terminal cleanup are unchanged. There is no
second TraCI controller and no physical or simulated signal-priority controller.

The runtime receives a Chennai-specific catalogue of 12 distinct legal routes,
generated by Dijkstra on SUMO lane connections and permission checks. Alternatives
are generated by excluding individual edges and sampling diverse paths across
the journey. Runtime normalization/validation checks each suffix at the actual
vehicle position. This is a bounded catalogue, not an exhaustive route search.
The existing topology supplier remains available elsewhere; S08 edge IDs are
never used by this pilot. Replanning is driven by actual observed costs and
existing policy thresholds, not imposed P0/P1/P2 timestamps.

## Geography and import

Source: [OSM API extract](https://www.openstreetmap.org/api/0.6/map?bbox=80.125,12.815,80.185,12.865).
The public Overpass endpoints returned HTTP 406/500; the OSM map API succeeded.
The original XML, import typemap, network, route metadata, geography and provenance
are committed under `simulation/chennai/network/`. Attribution: © OpenStreetMap
contributors, [ODbL 1.0](https://www.openstreetmap.org/copyright).

OSM way [336095563](https://www.openstreetmap.org/way/336095563) maps the VIT Chennai
campus around the requested reference 12.8408 N, 80.1540 E. The import envelope is
80.132–80.174 E, 12.823–12.863 N (about 4.6 × 4.4 km). Full edge geometries can
extend beyond that envelope. The simulation retains primary/tertiary corridors,
hospital access, legal alternatives and connecting feeder roads: **795 edges**.
It intentionally omits most residential cul-de-sacs, not roads invented for a demo.
The resulting complete edge shapes span 80.13067–80.17485 E and
12.81874–12.86433 N (approximately 4.8 × 5.1 km).

The road journey is longer than the area's straight-line span: the 12 catalogue
paths are approximately 7.45–8.79 km because divided roads, legal turns and access
connections constrain travel. Projection and offset metadata are preserved.
The source includes 61 explicitly one-way-tagged features and one no-right-turn
relation. Netconvert imports directionality, permissions and available restrictions;
all catalogue routes are checked against its resulting legal connections.
OSM topology is not a survey of every current turn rule or road condition.

Rebuild from the committed source (no network required):

```sh
venv/bin/python -m citybrain.chennai.build
# Explicitly replace the source from OSM, then rebuild:
venv/bin/python -m citybrain.chennai.build --download
```

The pinned SUMO OSM typemap is bundled to handle a macOS framework's unusual
`SUMO_HOME` layout. Import warnings are recorded, including tight junction geometry
and roundabout warnings. The pilot's actual route execution was independently
verified; these warnings do not establish that every imported side road is valid.

## Demand, incidents and signals

NORMAL/HEAVY/PEAK generate 0.7/1.4/2.2 vehicles per simulated second for 850 s,
using 90 seeded, legal background routes. These are synthetic, uncalibrated demand
profiles. Vehicles enter, accelerate, interact at junctions and form actual queues.
The ambulance departs at 40 s and dispatch occurs once the unchanged planner can
accept a usable route. Seed 17 is the reproducible default.

Two roadworks changes reduce actual SUMO lane speed limits to 1 m/s for 85 s.
The scenario considers changes after 90 and 210 s, and waits until the accepted
route has a future edge with a legal surviving diversion. Therefore the second
change may occur much later than 210 s. Changes and restorations are logged.
They do not prescribe the planner's response or guarantee any revision count.

No mapped OSM signal junctions survived the selected corridor. **Two synthetic
SUMO signal programs** are explicitly assigned at real junctions
`7732945699` and `cluster_1945600982_308878067`. Telemetry reads their actual phase
and per-link red/yellow/green states. These are not claims about physical lights
near VIT. CityBrain recommendations remain advisory and no signal writes occur.

## Viewer, telemetry and isolation

`dashboard/cesium/` includes local CesiumJS 1.121.0 (Apache-2.0), license notices
and a per-file SHA-256 manifest. No token or paid service is required. The baseline
uses ellipsoid terrain, local OSM roads and OSM building footprints. Heights from
building levels use an estimated 3 m per level; buildings without height data use
an explicitly estimated 6 m extrusion. This is not surveyed terrain or photogrammetry.
Clicking an entity exposes its source/height description in the map notice.

Vehicle boxes and screen-space markers are enlarged for presentation. Positions,
heading, speed, category, edge and time are actual SUMO observations. The viewer
does not advance vehicles, predict positions, extrapolate trajectories or run its
own traffic simulation. Map controls provide camera movement, ambulance follow,
an optional attributed OSM raster basemap and a local SVG 2D fallback.

The GET-only server binds `127.0.0.1`. It shares the existing dashboard's evidence
reader/reducer, not its S08-specific 3D scene. It adds `/api/geography` and Chennai
telemetry to `/api/state`; replay accepts a finite, nonnegative `?at=` timestamp.
The compact stream omits duplicated full planner inputs, candidate components
and repeated plan recommendations; full raw runtime evidence remains on disk.
Only the pilot's in-memory runtime evidence cache is bounded to 64 recent records.

Telemetry exceptions, external-provider exceptions and dashboard write failures
are isolated from runtime control. Closing the browser has no effect on SUMO.
Runtime output always uses a fresh directory outside `experiments/results`.
After completion the default launcher keeps the final dashboard available until
Ctrl-C. No-route, teleportation, timeout, interruption and execution failures are
reported as outcomes rather than being converted into successful arrivals.

## External traffic and GPS

`TrafficProvider` defines a provider-independent observation boundary. Replay
contains segment ID, coordinates, speed, free-flow speed, travel time, congestion,
incident, provider timestamp, freshness and source. Matching requires an explicit
segment-to-edge table and a geometric distance of at most 30 m. Unmatched/stale
observations stay labeled and never overwrite SUMO road measurements.

HERE/TomTom classes currently return **UNAVAILABLE**. They are interface placeholders,
not implemented live HTTP clients. No `HERE_API_KEY` or `TOMTOM_API_KEY` was present;
no live coverage or licensing test was performed and no billable request was made.
Relevant official interfaces investigated:
[HERE Traffic v7 flow](https://docs.here.com/traffic-api/docs/flow) and
[TomTom flow-segment data](https://docs.tomtom.com/traffic-api/documentation/tomtom-maps/v1/traffic-flow/flow-segment-data).
HERE supplies regional flow with location references; TomTom's endpoint supplies
the road fragment nearest a requested point. Either needs validated segment
geometry/direction matching before it could influence a simulation.

The GPS module accepts only labeled `GPS_REPLAY` records, requires explicit active
consent flags, validates coordinates/time/accuracy, and expires observations after
120 s. The bundled feed is **synthetic**, contains no person's location, and uses
a recorded-time clock anchored to simulation time. GPS markers are separate from
SUMO vehicles. There is no mobile endpoint, real GPS collection, authentication
service or public location history. Real ingestion remains future work.

## Validation and evidence

Run `venv/bin/python -m pytest -q` and:

```sh
venv/bin/python -m citybrain.chennai.validate \
  --run data/output/chennai/smoke-01 --historical
```

`docs/chennai/validation.json` contains the independent streamed audit: successful
physical route read-back before each acceptance, legal route transitions, actual
arrival evidence, changing signals, vehicle movement and geographic alignment.
The historic manifest is read directly from the existing frozen evidence archive.
No official trial is regenerated. `tests/test_chennai_sumo.py` additionally runs
actual dispatch followed by an unreachable hospital and verifies NO_ROUTE cleanup,
and starts both higher demand profiles in SUMO. Long HEAVY/PEAK response completion
and parameter calibration have not been validated.
